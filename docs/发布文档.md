# 发布文档

> 本文说明如何把「Dascle」作为一个正式版本发布到 GitHub Releases。
> 目标读者是维护者本人。构建、签名、安装的基础知识见[部署文档](部署文档.md)。

发布方式为**手动**：本地打 release 包 → 推到 GitHub → 在网页上创建 Release 并上传 APK。
（想改成「打 tag 自动出 Release」，见第 8 节。）

## 1. 发版清单

每次发版照着走一遍：

- [ ] 改 `app/build.gradle.kts` 的 `versionCode`（必须比上一个大）与 `versionName`
- [ ] 跑预检：`spotlessCheck` / `testDebugUnitTest` / `verifySqlDelightMigration`
- [ ] 确认根目录有 `keystore.properties` 且指向正式 keystore
- [ ] `clean assembleRelease` 打出 release APK
- [ ] 在真机上安装验证（混淆后不能崩）
- [ ] 留存 `mapping.txt`
- [ ] 提交改动并打 tag（`v1.0.0` 形式）推送到 GitHub
- [ ] 在 GitHub 网页创建 Release，上传 APK，写清更新说明
- [ ] **确认这条 Release 是「正式版」而不是「预发布」**（见第 7 节，勾错了 App 的「检查更新」会一直查不到）

## 2. 一次性准备：正式签名密钥

> ⚠️ 这一步只能做一次，并且必须长期保存好。
> 一旦用某个密钥发布了版本，后续所有版本都**只能**用同一个密钥签名，
> 否则老用户无法覆盖安装升级（只能卸载重装，数据全丢）。

用 JDK 自带的 `keytool` 生成密钥（本机 JDK 21 已自带 `keytool`）：

```powershell
keytool -genkeypair -v -keystore D:\keys\dascle-release.jks -alias dascle `
  -keyalg RSA -keysize 4096 -validity 10000 -storetype PKCS12
```

- `-validity 10000`：约 27 年有效期，够用。
- 会依次询问 keystore 密码、姓名 / 组织等信息，密码务必记牢。
- `D:\keys\` 这个目录建议在仓库**之外**，避免误提交。

然后在**仓库根目录**新建 `keystore.properties`（已在 `.gitignore` 中，不会提交）：

```properties
storeFile=D:/keys/dascle-release.jks
storePassword=你的store密码
keyAlias=dascle
keyPassword=你的key密码
```

`storeFile` 建议写绝对路径（构建脚本按 `file(...)` 解析，相对路径会以 `:app` 模块目录为基准）。

**备份清单**（建议云盘 + 本地各一份）：

- `dascle-release.jks` 文件本身
- `storePassword` / `keyAlias` / `keyPassword`

> 密钥丢失 = 无法再给已安装用户推送更新，只能换包名重新发一个 App。

### 2.1 副作用：debug 包也改用这个密钥

`app/build.gradle.kts` 的签名逻辑是「用 `keystore.properties` 覆盖名为 `debug` 的 signingConfig」，
而 debug 与 release 共用它。所以配好密钥之后：

- `assembleDebug` / `installDebug` 产出的包也由这个正式密钥签名；
- 如果设备上已经装过**旧的** debug 包（用 Android 默认 debug key 签的），直接安装会报
  `INSTALL_FAILED_UPDATE_INCOMPATIBLE`，需要先卸载旧包：

```powershell
adb uninstall com.fitplan.app.dev
```

（这只是开发环境的麻烦，不影响正式分发。）

## 3. 改版本号

版本号硬编码在 `app/build.gradle.kts`：

```kotlin
versionCode = 3
versionName = "1.1.1"
```

规则：

| 字段 | 规则 |
|---|---|
| `versionCode` | 正整数，**每次发版必须严格递增**，不能重复、不能回退。Android 靠它判断能不能覆盖安装 |
| `versionName` | 给用户看的字符串，用语义化版本 `主版本.次版本.修订号`，与 git tag 保持一致（tag 加 `v` 前缀） |

建议：修 bug → `1.0.1`；加功能 → `1.1.0`；不兼容的大改 → `2.0.0`。

## 4. 预检并打包

在仓库根目录执行（Windows 用 `.\gradlew.bat`）：

```powershell
.\gradlew.bat spotlessCheck
.\gradlew.bat testDebugUnitTest
.\gradlew.bat verifySqlDelightMigration

.\gradlew.bat clean assembleRelease
```

产物：`app/build/outputs/apk/release/app-release.apk`。

同时会产生反混淆映射表 **`app/build/outputs/mapping/release/mapping.txt`**——
务必连同 APK 一起留存（放到随版本命名的目录里）。以后用户报上来的崩溃堆栈是混淆过的，
没有对应版本的 `mapping.txt` 就基本看不出问题在哪。

一些打包细节：

- release 开启了 R8 混淆 + 资源压缩（`isMinifyEnabled` / `isShrinkResources`），
  所以**必须真机验证**，debug 包跑通不代表 release 能跑。
- release 的 `BuildConfig.BUILD_TIME` 取最近一次 git 提交时间，所以要先提交再打包。
- 输出是未对齐的 APK，直接安装没问题；AGP 会自动做 zipalign。

## 5. 真机验证

因为 debug 与 release 的包名不同（`com.fitplan.app.dev` / `com.fitplan.app`），
release 包是**全新安装**，不会继承 debug 的数据。

```powershell
adb install -r app\build\outputs\apk\release\app-release.apk
```

重点验证：

1. 冷启动不崩（R8 混淆最容易在这里翻车，例如序列化 / 反射相关的类被裁掉）。
2. 首次启动能正常导入 67 条内置动作。
3. 走一遍主流程：新建计划 → 编排动作 → 排到日历 → 开始训练 → 记一组 → 结束训练。
4. 统计页四张图能正常渲染。
5. 桌面添加「今日训练」组件，状态显示正确。
6. 设置页开启训练提醒，到点能收到通知。

顺手校验一下签名是不是正式密钥（`apksigner` 在 Android SDK 的 `build-tools` 下，
本机 SDK 装在 `D:\Install0\Android\Sdk`，`build-tools` 是 `37.0.0`）：

```powershell
& "D:\Install0\Android\Sdk\build-tools\37.0.0\apksigner.bat" verify --print-certs `
  app\build\outputs\apk\release\app-release.apk
```

输出里的 `Signer #1 certificate DN` 应该就是你生成密钥时填的信息，
而不是 `CN=Android Debug`（出现后者说明 `keystore.properties` 没被读到）。

## 6. 提交并打 tag

```powershell
git add app/build.gradle.kts
git commit -m "chore(release): 1.0.0"
git push origin main

git tag -a v1.0.0 -m "Dascle v1.0.0 首个正式版本"
git push origin v1.0.0
```

tag 命名统一 `v<versionName>`。打错要删（远端也要删）：

```powershell
git tag -d v1.0.0              # 删本地
git push origin :refs/tags/v1.0.0   # 删远端
```

## 7. 在 GitHub 上创建 Release

前置：先把 APK 重命名成带版本号的名字，避免每个版本的附件都叫 `app-release.apk` 分不清：

```powershell
Copy-Item app\build\outputs\apk\release\app-release.apk Dascle-1.0.0.apk
```

然后打开 <https://github.com/UnsleepingDawn/Dascle/releases/new>：

1. **Choose a tag**：选刚推上去的 `v1.0.0`（若下拉里没有，直接在输入框敲 `v1.0.0`，
   GitHub 会提示 `Create new tag: v1.0.0 on publish`）。
2. **Target**：确认是 `main`。
3. **Previous tag**：一般会自动选中上一个版本，用于生成变更列表。
4. **Release title**：填 `v1.0.0`（可附带一句主题，如 `v1.0.0 — 首个正式版`）。
5. 点右侧 **Generate release notes**，GitHub 会按 commit 自动生成分类好的更新说明，然后手动润色成中文。
6. **Attach binaries**：把 `Dascle-1.0.0.apk` 拖进附件区。
   （GitHub 单个附件上限 2 GB，我们的包只有几 MB，不是问题。）
7. **「Set as the latest release」/「Set as a pre-release」要选对**：
   选 **Set as the latest release**（默认就是它），**不要**勾 `Set as a pre-release`。
   原因见第 7.1 节——勾成预发布，App 的「检查更新」会一直查不到新版本。
8. 点 **Publish release**。

完成后 `https://github.com/UnsleepingDawn/Dascle/releases/latest` 就会指向这个版本——
README 里的下载链接用的正是这个地址，不用每次改。

### 7.1 为什么必须选「latest」而不是「pre-release」

被标成 `pre-release` 的 Release 会被 GitHub 的 **`GET /releases/latest`** 接口忽略：
这个接口只返回「最新的、非草稿、非预发布」的那一条，一条都没有时就返回 **404**。
历史教训：`v1.0.0` ~ `v1.1.1` 三条都被勾成了预发布，App 的「检查更新」在模拟器和真机上
一律显示「GitHub 暂时没有正常响应」——其实是 404，跟网络毫无关系。

两处防线：

- **发版时**：按上面的清单确认选的是 **Set as the latest release**。
  已经发错了就在 Release 编辑页取消 `Set as a pre-release` 勾选，立刻生效。
- **App 侧**：`GitHubReleasesApi` 已经改走 `GET /releases` 列表自己挑（优先非预发布，
  没有就退回非草稿的最新一条），所以就算标成预发布也能查到；同时 404 会有专门文案
  「GitHub 上还没发布可用的版本」，不再谎报「服务器没正常响应」。细节见《开发文档》§7.13。

### 更新说明写什么

建议包含三块，用户看得懂比什么都重要：

```markdown
## 新增
- xxx

## 修复
- xxx

## 安装
下载下方 `Dascle-1.0.0.apk`，在手机上安装。
从旧版本升级直接覆盖安装即可，数据不会丢失；首次安装需要允许「安装未知来源应用」。
```

## 8. 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| 安装新版本报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE` | 手机上装的是**另一个密钥**签的包（旧 debug 包，或换过 keystore）。卸载后重装，或找回原密钥 |
| `apksigner verify` 显示 `CN=Android Debug` | 根目录缺 `keystore.properties`，或 `storeFile` 路径不对，release 退回了默认 debug keystore |
| release 包一打开就崩，debug 正常 | R8 把需要的类裁掉了。看 `mapping.txt` 反混淆堆栈，往 `app/proguard-rules.pro` 加 keep 规则后重新发版 |
| 用户说「装上了但没更新」 | 忘了递增 `versionCode`，Android 认为不是新版本。递增后重新打包，**删掉旧 Release 的附件重传**，tag 也要重打 |
| App 点「检查更新」显示「GitHub 上还没发布可用的版本」 | 仓库里一条非草稿 Release 都没有。先发一个版本 |
| App 点「检查更新」一直说查不到新版本，但 Releases 页明明有 | 那些 Release 被勾成了「预发布」且用的是老版 App。取消 `Set as a pre-release` 勾选，或升级到走 `/releases` 列表的新版 |
| CI 报 `spotlessCheck` 失败 | 本地先 `.\gradlew.bat spotlessApply`，把格式化结果一起提交 |
| tag 推上去了才发现包不对 | 先删 GitHub Release，再删远端 tag（见第 6 节），改完重新走流程 |

## 9. 后续可自动化（暂未实施）

目前每次发版都要手动跑一遍。若以后嫌麻烦，可以新增
`.github/workflows/release.yml`，做到「推 tag 即出 Release」：

- 触发：`on: push: tags: ['v*']`
- 步骤：校验 → 从 GitHub Secrets 还原 keystore（`.jks` 转 base64 存进 `KEYSTORE_BASE64`）
  → `assembleRelease` → 用 `softprops/action-gh-release` 上传 APK 与 `mapping.txt`
- 需要把 workflow 权限设为 `contents: write`
- 代价：密钥材料要存进仓库 Secrets；`versionCode` / `versionName` 仍是硬编码，
  自动发版前得先提交版本号改动，再打 tag

这项改造建议先等手动流程跑顺一两次再考虑。
